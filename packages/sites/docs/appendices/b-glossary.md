# Glossary

> Every term the book uses that you might want to look up, in one or two
> sentences each, with a link to the section that teaches it. The first
> part holds MVT's own terms, and the general terms the book leans on. The
> second holds the names of the libraries and tools that the book uses
> for its examples.

**Related:** [MVT on One Page](a-mvt-on-one-page.md) ·
[The Eight Principles](../chapters/25-the-eight-principles.md) ·

An entry here is a reminder, not a lesson. If a definition leaves you with

with examples, and says why it matters.

## MVT Terms

| Term | Meaning |
| --- | --- |
| **Action** | A model's method for a one-off command from the player, named for what the player means, such as `startNewRun()`. The model still decides whether the action is allowed. [§](../chapters/04-models.md#actions-say-what-the-player-means) |
| **Advance, then orchestrate** | The two steps of a model's `update`. First it moves every clock and child model on by `deltaMs`, then it checks the result and starts whatever should come next. [§](../chapters/06-time-and-phases.md#advance-then-orchestrate) |
| **Audio test** | A test that checks what a sound sounds like, so that a sound changed by accident fails it. It does for sound what a visual test does for a view. [§](../chapters/20-sound-and-music.md#testing-an-audio-view) |
| **Audio view** | A view that plays sounds instead of drawing. It reads its bindings like any view, and plays a sound when a value changes in a way worth hearing. [§](../chapters/20-sound-and-music.md#audio-views) |
| **B- rules** | The binding rules, B-contract, B-reusable, B-optional and B-wiring, which say what a view's bindings are and where they're wired. [§](a-mvt-on-one-page.md#binding-rules) |
| **Bindings** | The plain object that a view receives when it's made. Its query bindings carry state in, its relay bindings carry the player's input out, and its type lists everything the view depends on. [§](../chapters/08-bindings.md#the-bindings-object) |
| **Change detection** | Comparing what you read now with what you read last time, and doing slow work only when the two differ. [Chapter 9, Noticing Changes](../chapters/09-noticing-changes.md) |
| **Changed per frame** | In the measurements, the share of Pixi containers that change in a frame, from 0% (a scene at rest) to 100%. [§](c-measurements.md#the-benchmark-setup) |
| **Cohesion, coupling** | A component is cohesive when its contents belong together and change for the same reasons. Components are loosely coupled when they depend on each other only through small, declared interfaces. [§](../chapters/26-separation-of-concerns.md#applied-to-mvt-cohesion-and-coupling) |
| **Command, query** | A command changes state and doesn't return a value. A query returns a value, and doesn't change any state that a caller can observe. [§](../chapters/28-command-query-separation.md#the-principle) |
| **Command-Query Separation (CQS)** | The principle that reading state never changes it. Each tick runs every command (`update`), then every query (`refresh`). [Command-Query Separation (CQS)](../chapters/28-command-query-separation.md) |
| **Component** | Any separable unit of an MVT program, such as a model, a view or the ticker. It isn't a JSX component, or a component in an entity component system. [§](../chapters/25-the-eight-principles.md#the-goal) |
| **Composite Reuse Principle (CRP)** | The principle of building bigger components by combining smaller ones, never by extending them. [Composite Reuse Principle (CRP)](../chapters/30-composite-reuse.md) |
| **Computed value** | A value worked out from the getters it watches, and worked out again only when one of them changes. It computes lazily, on its first read, and it's a getter itself. [§](../chapters/09-noticing-changes.md#computed-values-a-value-worked-out-from-others) |
| **Continuous state** | State that changes on most frames, such as a position. A view just reads it, without detecting changes. [§](../chapters/09-noticing-changes.md#when-to-use-change-detection) |
| **Contract** | What a component requires of its callers, and what it guarantees in return. A view's bindings type is its contract with the rest of the game. [§](../chapters/31-design-by-contract.md#the-principle) |
| **Cosmetic state** | Another name for presentation state. [§](../chapters/11-presentation-state.md#presentation-state-and-domain-state) |
| **Count** | A number in a model that rises by one each time a moment happens, such as `shotsFired`. It lets a view notice a moment that doesn't change any other state. [§](../chapters/09-noticing-changes.md#counts-moments-that-repeat) |
| **Declarative, imperative** | Declarative code says what should be true, such as "this sprite sits where the ship is", and leaves the steps to something else. Imperative code lists the steps. [§](../chapters/12-writing-views-in-jsx.md#is-a-jsx-view-really-declarative) |
| **Delete-the-view test** | The way to tell presentation state from domain state: if you deleted the view, would the game still play correctly? If not, the state belongs in a model. [§](../chapters/11-presentation-state.md#when-is-presentation-state-really-domain-state) |
| **Delta cap** | The ticker's limit on `deltaMs`, typically 100 ms, so that a long gap, such as a hidden tab, never reaches the models as one huge step. Every model must produce the same results at any step size up to the cap, and never has to handle a bigger step, as [Chapter 6](../chapters/06-time-and-phases.md#steps-of-different-sizes) explains. [§](../chapters/05-the-tick.md#the-delta-cap) |
| **`deltaMs`** | The number of milliseconds since the last frame, which the ticker passes to every `update`. It's the only way time reaches a model. [§](../chapters/04-models.md#the-update-deltams-contract) |
| **Dependency Inversion Principle (DIP)** | The principle that a component declares what it needs, as a small interface of its own, and the code that creates it supplies it, time included. [Dependency Inversion Principle (DIP)](../chapters/29-dependency-inversion.md) |
| **Design by Contract (DbC)** | The principle that every component states what it requires and what it guarantees, and fails loudly when either is broken. [Design by Contract (DbC)](../chapters/31-design-by-contract.md) |
| **Design for Testability (DfT)** | The principle that every component can be tested on its own, through its contract, with the same result every time. [Design for Testability (DfT)](../chapters/33-design-for-testability.md) |
| **Deterministic** | A model is deterministic when the same series of `update` calls, with the same input between them, always leaves it in the same state. [§](../chapters/04-models.md#the-update-deltams-contract) |
| **Dirty checking** | Finding a change by comparing a value with what it was, rather than waiting for a notification. MVT's change detection works this way. [§](../chapters/10-why-views-poll.md#other-approaches-to-reactivity) |
| **Discrete state** | State that changes now and then, such as a score or a phase. A view notices its changes, so that slow work runs only when it changes. [§](../chapters/09-noticing-changes.md#when-to-use-change-detection) |
| **Domain coordinates** | Positions, distances and speeds in units that mean something in the game, such as tiles or world units, never pixels. Views convert them for the screen. [§](../chapters/04-models.md#domain-coordinates) |
| **Domain logic** | The rules that change domain state, such as collisions and scoring. They belong in models, where a test can check them without drawing anything. [§](../chapters/04-models.md#splitting-concerns-between-model-and-view) |
| **Domain state** | The state that decides the game's outcomes, such as positions, scores and phases. Models own it, and it never depends on presentation state. [§](../chapters/02-why-mvt.md#two-kinds-of-state) |
| **Dynamic property** | In the measurements, a property of a Pixi container that is updated from the model every frame. Its opposite is a static property. [§](c-measurements.md#the-benchmark-setup) |
| **Effect** | In a library of signals, code that reads signals, and that the library runs again whenever one of them changes. [§](../chapters/10-why-views-poll.md#three-ways-to-detect-a-change) |
| **Entity component system (ECS)** | A way of building game objects from pieces of plain data, its own "components", which separate systems process. It works at a different level from MVT, and the two fit together. [§](../chapters/30-composite-reuse.md#common-misreadings) |
| **Events** | A way of learning about a change in which the model sends a named notification, and each listener that registered for it runs at once. It's also called the observer pattern. [§](../chapters/10-why-views-poll.md#three-ways-to-detect-a-change) |
| **Factory function** | A function named `createXxx` that takes one options object and returns a plain object that matches an interface. This book writes models this way, but MVT doesn't require it. [§](../chapters/04-models.md#writing-a-model-as-a-factory) |
| **Fixed value** | A query binding given as a plain value, such as `tileSize: 20`, rather than a getter. The view reads it once, when it's made. A binding declared as a plain `T` takes only a fixed value, so its type says the view won't follow a change. [§](../chapters/08-bindings.md#fixed-values-and-getters) |
| **Forced layout** | The layout work that a browser must do at once when code reads a size after writing to the page. A refresh step that forces it for each element can make a frame late. [§](../chapters/21-reading-layout-back.md#why-not-measure-in-the-refresh-step) |
| **Frame** | The browser's call to the ticker each time it's about to draw a new picture. A running game ticks once a frame, so "every frame" and "every tick" usually mean the same, but a test ticks without any frames, a paused game has frames whose models aren't ticked, and fast-forward can tick the models many times in one frame. [§](../chapters/05-the-tick.md#ticks) |
| **Frame sequence** | The fixed order of every tick: the models update, the views update their presentation state, the views refresh, and the renderer draws. [§](../chapters/05-the-tick.md#the-frame-sequence-in-detail) |
| **Game engine** | A program that provides a whole way of making a game: drawing, sound, input, physics, and a loop that calls your code once a frame. The game's state usually lives in the engine's own objects. Phaser, Unity and Godot are examples. MVT can work inside one, with one script as the ticker. [§](../chapters/01-games-in-the-browser.md#game-engines) |
| **Game loop** | A loop that runs once a frame, and drives the simulation and then the presentation. MVT's ticker is a game loop. [§](../chapters/05-the-tick.md#ticks) |
| **Garbage** | Objects, arrays, strings and functions that the program doesn't use any more. The JavaScript engine pauses now and then to reclaim them, so code on a hot path avoids making them. [§](../chapters/23-why-performance-matters.md#garbage-turns-into-pauses) |
| **`get` accessor** | A property defined with `get`, such as `get score() { return score; }`, which runs a function each time it's read. Reading `model.score` returns a value, not a getter, so pass `() => model.score` where a getter is expected. [Code Style](../working-in-this-repo/code-style.md#getter-setter-pairs) |
| **Getter** | A function that takes no arguments and returns a current value, such as `() => model.score`. A view calls the getters that it receives every frame. [§](../chapters/08-bindings.md#query-bindings) |
| **GSAP timeline** | A timeline from GSAP, a popular animation library. A model can use one, as long as it creates it paused and moves it on in `update`. [§](e-timelines-with-gsap.md#why-a-model-needs-a-paused-timeline) |
| **H- rules** | The hot-path rules, H-cost, H-alloc, H-loops and H-change, which keep code that runs every tick fast. [§](a-mvt-on-one-page.md#hot-path-rules) |
| **Hot path** | Code that runs every tick: a model's `update`, a view's `update` and `refresh`, and everything they call. [§](../chapters/24-hot-paths.md#code-that-runs-on-a-hot-path) |
| **Idempotent** | A `refresh()` is idempotent when calling it twice with the same state produces the same output as calling it once. [§](../chapters/07-views.md#the-refresh-contract) |
| **Immediate-mode data flow** | How a view reads: every frame, it reads all the state it shows, as if it were drawing from scratch. [§](../chapters/07-views.md#immediate-mode-data-flow-retained-mode-output) |
| **Invariant** | What is always true of a component between calls. [§](../chapters/31-design-by-contract.md#the-principle) |
| **Leaf view** | A view of a single game object, a HUD or an overlay, which takes query and relay bindings rather than the model, so it can be reused and tested alone. Chapter 8 calls it a reusable view. [§](../chapters/08-bindings.md#when-to-pass-the-whole-model) |
| **M- rules** | The model rules, M-time, M-isolation, M-domain and M-composition, which say how a model gets its time and what it may reference. [§](a-mvt-on-one-page.md#model-rules) |
| **Make Illegal States Unrepresentable (MISU)** | The principle of shaping state so that a combination that doesn't make sense can't be written, such as one `phase` in place of several flags. [Make Illegal States Unrepresentable (MISU)](../chapters/32-make-illegal-states-unrepresentable.md) |
| **Model** | The part of an MVT program that owns domain state and the rules that change it. It moves forward in time only through `update(deltaMs)`, and doesn't reference any view. [Chapter 4, Models](../chapters/04-models.md) |
| **Model tree** | Models made of models. The ticker updates the root, and each parent calls its children's `update`, then handles the work that spans them, such as collisions. [§](../chapters/04-models.md#trees-of-models) |
| **MVT** | Model-View-Ticker: an architecture that assigns a game's three jobs, deciding what happens, showing it and keeping time, to three parts. [§](../chapters/02-why-mvt.md#three-jobs-three-owners) |
| **MVVM** | Model-View-ViewModel, a pattern for user interfaces in which a ViewModel sits between the view and the model, and adapts the model's state for the view. MVT's bindings are close to its data binding. MVT's view model takes its name from the ViewModel, but is narrower. [§](../chapters/18-growing-a-complex-view.md#extract-a-view-model) |
| **Open-ended phase** | A phase that waits for something to happen, rather than ending after a set time, such as a chest that stays open until something closes it. Its progress stays at 1, and only an action moves the model on. [§](../chapters/06-time-and-phases.md#open-ended-phases) |
| **Passive View** | A form of Model-View-Presenter in which a presenter reads the model and pushes each value into a view that doesn't have any logic. MVT's views share its aim of keeping domain logic out of views, but they read the state themselves, every frame. [§](../chapters/02-why-mvt.md#patterns-you-may-know) |
| **Phase** | The named stage something is in, such as `'opening'` or `'open'`, given as a string-literal union. A model is in exactly one phase at a time. [§](../chapters/06-time-and-phases.md#phases-and-progress) |
| **Polling** | Learning about a change by reading the current state at a point that comes round regularly. MVT views poll, in `refresh()`. [§](../chapters/10-why-views-poll.md#three-ways-to-detect-a-change) |
| **Practices** | Habits the book teaches that follow from MVT's rules but aren't rules themselves, such as actions that say what the player means. Appendix A lists them, each with a link to where it's taught. [§](a-mvt-on-one-page.md#practices-the-book-teaches) |
| **Pool** | A set of objects made once and reused, such as the views of short-lived bullets, so that objects aren't built or destroyed every frame. [§](../chapters/14-lists-and-switches.md#pools-of-short-lived-items) |
| **Presentation state** | State that a view keeps only for how things are shown, such as how far a fade has got. The view owns it, keeps it private, and moves it on in its own `update(deltaMs)`. [§](../chapters/11-presentation-state.md#presentation-state-and-domain-state) |
| **Principles** | The eight design principles that MVT's rules come from: SoC, SSOT, CQS, DIP, CRP, DbC, MISU and DfT. Each has a chapter of its own. [§](../chapters/25-the-eight-principles.md#the-eight-principles) |
| **Progress** | A number from 0 to 1 that says how far through its current phase a model is. [§](../chapters/06-time-and-phases.md#phases-and-progress) |
| **Push** | Any way of learning about a change in which the side that changed starts the work, as events and signals do. Its opposite is polling. [§](../chapters/10-why-views-poll.md#three-ways-to-detect-a-change) |
| **Query binding** | A binding that the view reads for the state it shows, such as a position or a score. It's a fixed value, a getter, or a function with arguments such as `tileKindAt(row, col)`, and it never changes any state. [§](../chapters/08-bindings.md#query-bindings) |
| **Reaction** | A function you call on every step. Each call reads the getter it watches, and runs its `react` callback when the value has changed in a way its `when` accepts. It never reacts to its first read. [§](../chapters/09-noticing-changes.md#reactions-do-something-when-a-value-changes) |
| **Reactivity** | The general name for how views find out about a change. The three broad ways are events, signals and polling. [§](../chapters/10-why-views-poll.md#three-ways-to-detect-a-change) |
| **Recognised gesture** | Input that a view works out from simpler events, such as a long press from a press and the time that passes. A view model usually times it, and reports it after the frame. [§](../chapters/18-growing-a-complex-view.md#example-a-press-that-turns-into-a-hold) |
| **Reduced motion** | A setting people choose when large movements on screen make them dizzy or sick. It's presentation, so the views read it through a binding, and the model never references it. [§](../chapters/22-reduced-motion.md#motion-is-presentation) |
| **Refresh step, `refresh()`** | A view's step that reads state and writes the view's output, once a tick, after every model has updated. It's reactive, idempotent and read-only, works with no time involved, and never reads back what it wrote. [§](../chapters/07-views.md#the-refresh-contract) |
| **Relay binding** | A binding the view calls to report input, which is usually what the player did, such as `onFirePressed`. It's named for what happened, the wiring decides what it means, and the view calls it only between frames. [§](../chapters/08-bindings.md#relay-bindings-and-input-handling) |
| **Renderer** | Whatever draws a view's output, such as Pixi, three.js or the browser's DOM. It draws after the views have refreshed. [§](../chapters/07-views.md#the-role-of-a-view) |
| **Requirement, guarantee** | A requirement (a *precondition*) is what must be true before a call, and meeting it is the caller's job. A guarantee (a *postcondition*) is what will be true after it, and keeping it is the component's job. [§](../chapters/31-design-by-contract.md#the-principle) |
| **Retained-mode output** | How a view writes: it builds its display objects once, and `refresh()` sets their properties. [§](../chapters/07-views.md#immediate-mode-data-flow-retained-mode-output) |
| **Scene graph** | A renderer's tree of display objects, such as Pixi's containers or the page's HTML elements. You create a display object once and change its properties, and the renderer draws it as it is now. [§](../chapters/01-games-in-the-browser.md#renderers) |
| **Separation of Concerns (SoC)** | The principle of keeping different jobs apart, each with its own owner. MVT's three are deciding what happens, showing it and keeping time. [Separation of Concerns (SoC)](../chapters/26-separation-of-concerns.md) |
| **Signal** | A value kept in a small container. A runtime records which effects read it, and runs them again when it changes, as Solid's `createSignal` does. [§](../chapters/10-why-views-poll.md#three-ways-to-detect-a-change) |
| **Single Responsibility Principle (SRP)** | Cohesion taken to its limit: a module should be responsible to one group of people whose requests change it. [§](../chapters/26-separation-of-concerns.md#applied-to-mvt-cohesion-and-coupling) |
| **Single Source of Truth (SSOT)** | The principle that each piece of domain state lives in exactly one model. Everything else reads it, or works out what it needs from it, and doesn't keep a copy. [Single Source of Truth (SSOT)](../chapters/27-single-source-of-truth.md) |
| **Spiral of death** | A loop that runs the models in fixed steps, several a frame when it's behind, falls further behind every frame if each step takes longer than the time it covers. A ticker that updates the models once a frame never has this problem. [§](../chapters/05-the-tick.md#the-delta-cap) |
| **Stateless view** | In this book, a view that doesn't hold any domain state. It still holds its display objects, and it may hold presentation state. [§](../chapters/07-views.md#the-role-of-a-view) |
| **Stand-in binding** | A getter or function that a test supplies in place of a model's, such as `() => 100` for a bullet's position. It lets a test put a view in any state without building a game. [§](../chapters/16-testing-views.md#the-steps-of-a-view-test) |
| **Static property** | In the measurements, a property of a Pixi container that is set once, when the scene is built, and doesn't take any time per frame. [§](c-measurements.md#the-benchmark-setup) |
| **Static state** | State that never changes while the game runs, such as a tile size. A view reads it once, when it's made. [§](../chapters/09-noticing-changes.md#when-to-use-change-detection) |
| **T- rules** | The ticker rules, T-sequence, T-cap, T-minimal and T-control, which say what the ticker does each frame, and what it never does. [§](a-mvt-on-one-page.md#ticker-rules) |
| **Tick** | One turn of the ticker's loop. Ticking a model calls its `update(deltaMs)`, and ticking a view calls its `update(deltaMs)`, if it has one, then its `refresh()`. [§](../chapters/05-the-tick.md#ticks) |
| **Ticker** | The part of an MVT program that keeps time. Each frame, it measures `deltaMs`, ticks the models, then the views, and then calls the renderer to draw. [Chapter 5, The Tick](../chapters/05-the-tick.md) |
| **Timed phase** | A phase with a set duration. Its progress runs from 0 to 1, and the model moves on by itself when the time is up. Its opposite is an open-ended phase. [§](../chapters/06-time-and-phases.md#open-ended-phases) |
| **Time control** | Pausing, slow motion, fast forward, stepping and replay, all done by the ticker choosing which `deltaMs` to pass. [§](../chapters/05-the-tick.md#time-control) |
| **Top-level view** | The view at the top of a game, which wires the game's views together. Its one binding is the model itself, since it won't be reused. [§](../chapters/08-bindings.md#when-to-pass-the-whole-model) |
| **UI framework** | A library that structures a web app as components built from its state, and updates the page when the state changes, such as React, Vue or Solid. It suits pages that are mostly still. [§](../chapters/01-games-in-the-browser.md#ui-frameworks) |
| **Unidirectional data flow** | State flows one way: from the models to the views through query bindings, and the player's input back to the models through relay bindings. [§](../chapters/27-single-source-of-truth.md#state-flows-one-way) |
| **Update Method** | A pattern from game programming in which each object has a method that the game loop calls once a frame. A model's `update(deltaMs)` is one. [§](../chapters/04-models.md#the-update-deltams-contract) |
| **Update step** | A view's own `update(deltaMs)`, which only a view with presentation state has. It moves that state on, doesn't write any output, and accepts a `deltaMs` of 0. [§](../chapters/11-presentation-state.md#a-view-s-update-deltams) |
| **`update(deltaMs)`** | A model's one way to move forward in time, which the ticker calls each frame. A view with presentation state has one too, its update step. [§](../chapters/04-models.md#the-update-deltams-contract) |
| **V- rules** | The view rules, such as V-reactive, V-idempotent and V-readonly, which say what a view may hold and which rules its refresh step follows. [§](a-mvt-on-one-page.md#view-rules) |
| **Version** | A number that rises whenever a structure may have changed, such as a model's `gridVersion`, so that a view can watch the structure through a primitive. [§](../chapters/09-noticing-changes.md#reading-state-you-don-t-watch) |
| **View** | The part of an MVT program that shows the model's state. It reads the state through its bindings, writes it to an output such as a Pixi container, the DOM or a speaker, and doesn't hold any domain state. [§](../chapters/07-views.md#the-role-of-a-view) |
| **View model** | A plain object that one view makes and owns, holding only presentation state, or a gesture's timing, and the rules that coordinate it, with an `update(deltaMs)` of its own. It doesn't touch any display objects, so you can test it alone. It takes its name from MVVM's ViewModel, but is narrower, since it doesn't adapt domain state for a view. [§](../chapters/18-growing-a-complex-view.md#extract-a-view-model) |
| **View tree** | Views made of views. Each parent view builds its children and wires their bindings, and the tree doesn't need to match the model tree. [§](../chapters/13-composing-views.md#parent-views-wire-their-children) |
| **Visual test** | A test that builds a view in a known state, makes an image of it, and compares that with its reference image. [Chapter 17, Visual Tests](../chapters/17-visual-tests.md) |
| **Wall clock** | The real time, as `setTimeout`, `setInterval`, `requestAnimationFrame` and `Date.now()` measure it. A model never uses it, since time reaches it only as `deltaMs`. [§](../chapters/04-models.md#things-to-keep-out-of-a-model) |
| **Watcher** | A tool you poll once in each step. Its reading reports, for each getter it watches, the current and previous values and whether the value changed. [§](../chapters/09-noticing-changes.md#watchers-what-changed-for-logic-in-a-step) |
| **Wiring** | The code that makes a view, and supplies each of its bindings: query bindings from the models or with fixed values, relay bindings with the models' methods. [§](../chapters/08-bindings.md#wiring-bindings) |

## Terms From the Book's Libraries

These come from the `@mvtjs` libraries, `audio90` and v-snap. MVT doesn't
require any of them. They're one way of meeting its rules, and the book's
examples use them.

| Term | Meaning |
| --- | --- |
| **Actual image** | The image a visual test makes on this run. When it differs from the reference image, the test fails, and v-snap keeps the actual image and a diff for you to look at. [§](../chapters/17-visual-tests.md#reviewing-a-change) |
| **`advanceTime`** | A test helper that moves models and views on by some milliseconds, in steps of 16 ms, updating the models before the views. It doesn't refresh. Always `await` it. [§](../chapters/15-testing-models.md#moving-time-on-with-advancetime) |
| **Attribute** | In JSX, a `name={value}` on a tag. On an intrinsic element it sets a property, and on a view's tag it supplies one of the view's bindings. Other JSX libraries call these *props*. [§](../chapters/12-writing-views-in-jsx.md#setting-up-a-jsx-file) |
