# Proposal: the website, and one Arcade for every entry

> Move `site/` to `packages/website/`, and replace the Pixi cabinet (`/games/`) and
> the demos gallery (`/demos/`) with one **Arcade**: the site's home page, a
> wall of cards in several columns for every game, demo and (later) art piece,
> whatever it renders with, filterable by tags. The Arcade is
> written in HTML JSX, the MVT way, and keeps the cabinet's zoom into and
> out of an entry. Measured, the 5 second first load is a chain of serial
> round trips, not CPU work. The Arcade removes most of that chain, so it needs no
> site-wide loading screen, just a progress bar held inside the zoom when
> an entry takes longer to load than the zoom takes to play.

## 1. Background

The site has two places that list things to run, and they share almost
nothing:

- **`/games/`, the cabinet.** One Pixi `Application` fills the page. A Pixi
  view (`CabinetView`, 552 lines of hand-placed carousel) shows the games
  and zooms into one when it launches. On startup, `main.ts` loads every
  game's textures and starts each game headless to render its thumbnail,
  and only then builds the cabinet. Until that finishes, the page under the
  nav bar is black. The host owns the games' chrome: pause menu, touch
  controls, keyboard input, integer scaling, orientation hint.
- **`/demos/`, the gallery.** A hand-written DOM grid of cards built in
  `demos/main.ts`, with Run and Info buttons. A demo runs in a fresh Pixi
  `Application`. Thumbnails are rendered by a second, hidden Pixi app after
  the grid shows. `DemoEntry` starts on a Pixi `Container`, so the two demos
  that are not purely Pixi (Boids in 3D on three.js and HTML, and the Fruit
  Machine on Pixi, three.js and HTML) are separate pages, linked from the
  gallery's subtitle. Task 026 was raised to fix that.

`GameEntry` and `DemoEntry` are close cousins (id, name, screen size,
`thumbnailAdvanceMs`, `load`, `start(stage)`), differing in games' input
configuration and instructions and demos' description and techniques.

## 2. The site becomes the website package

`site/` is already a private workspace package (named `site`), but it sits
outside `packages/`. It moves to `packages/website/`, as package `@mvtjs/website`,
so the repo's source code lives in packages. It is private and not a
library, like `packages/eslint-plugin` already is.

**Scoped names.** Every package is named under `@mvtjs`, published or not.
The bare names `website`, `docs`, `benchmarks` and `checks` all belong to
strangers' packages on npm. A private workspace under one of them resolves
locally only while npm knows about the workspace. Anything that resolves
from the registry instead would fetch the stranger's package (dependency
confusion). Nobody else can publish under `@mvtjs`. An import from
`@mvtjs/website/games` also reads as this repo's at a glance. Changesets
leaves a private `@mvtjs` package alone, despite the `@mvtjs/*` fixed group:
`@mvtjs/eslint-plugin` stayed at 0.1.0 through the 0.2.0 release.

Nothing in the repo assumes everything in `packages/` is published:

- **Changesets** never versions or tags a private package
  (`privatePackages: { version: false, tag: false }` in
  `.changeset/config.json`).
- **ESLint** has no rule scoped to `packages/*/src` because those are
  libraries. The site's own rules (models without wall-clock time, the
  playground's import boundaries) move from `site/src/**` to
  `packages/website/src/**`. The barrel-import block's
  `['site/src/**', 'packages/*/src/**']` becomes just `packages/*/src/**`.
- **`build:packages` needs one change.** It runs `npm run build -w packages`,
  which runs the `build` script of every workspace under `packages/`. Today
  that includes the eslint plugin; after the move it would include a Vite
  build of the website. Name the four libraries instead
  (`-w @mvtjs/utils -w @mvtjs/pixi -w @mvtjs/three -w @mvtjs/html`), which
  also says what the script is for.

It is done first, alone, as a move with only the references changed, so that
history follows the files and the later diffs are about the Arcade alone.

What references `site`:

- Root `package.json`: `workspaces` (the `site` line goes; `packages/*`
  covers it), and the scripts `dev`, `build`, `build:site` (becomes
  `build:website`), `build:packages` (above), `preview`, `generate-textures`.
- `vite.config.ts`: the build's `outDir` (`../dist` becomes `../../dist`,
  so the Pages output stays at the repo root, beside the docs build).
- `.github/workflows/deploy.yml` and `test-deploy.yml` (`npm run build:site`).
- `tsconfig.json` (project reference), `vitest.config.ts`, and
  `eslint.config.js` (ten `site/src` paths and globs, including the playground's
  import boundaries, and the import resolver's `./site/tsconfig.json`, which
  `./packages/*/tsconfig.json` then covers).
- `packages/benchmarks/suites/games-and-demos.case.ts` and
  `falling-sand-scaling.case.ts` import `../../site/src/games` and
  `../../site/src/demos` by relative path, past the package boundary. The
  "Declared dependencies" convention says to import a package by name, so
  the move is the time to fix this: `website/package.json` gains
  `exports` for the entry list (section 6.4), and `benchmarks` declares
  `@mvtjs/website` as a dependency.
- Docs and agent instructions: `AGENTS.md`, `README.md`,
  `packages/docs/reference/project-structure.md`, four `packages/docs/ai-agents/` files, three
  guide pages, and the games' and demos' READMEs, about 25 mentions in all.
- Open notes (019, 022, 034, 035, tasks 017 and 026). Archived notes keep
  their paths, as `notes/README.md` already says for 011's move. Add
  "`site/` is now `packages/website/`" to its "Paths in older notes"
  paragraph.

The `#shared` import alias and the `scripts/` directory move unchanged.

**The other workspaces follow.** `docs/`, `benchmarks/` and `checks/` move
into `packages/` too, each in a commit of its own (section 12, question 8),
so `packages/` holds all of the repo's source and the top level keeps only
configuration and `notes/`.

In the rest of this proposal, `website/` is short for `packages/website/`.

## 3. Load time, measured

### 3.1 Method

A Node script drove headless Chrome over the DevTools protocol, with the
browser cache disabled. It sampled screenshots every ~150 ms, and counted
the bright pixels below the nav bar to find when content first appeared. It
also read the page's resource timings and long tasks, and recorded a CPU
profile of the local build. The machine was a laptop with an RTX 4070 (WebGL
on the GPU, not a software renderer), at 1280x800, with
`devicePixelRatio` 1. Each run launched Chrome once, with one profile (see
the Chrome profile lockout note in `packages/benchmarks/harness/driver.ts`). The
script lived in the session's scratch space, not in the repo. Section 11's
step 6 would make it a repeatable check.

### 3.2 Results

| Page | Condition | DOM ready | Last request done | Content visible |
| --- | --- | ---: | ---: | ---: |
| `/games/` | deployed, first load of run 1 | 1.26 s | 4.18 s | **4.58 s** |
| `/games/` | deployed, first load of run 2 | 1.41 s | 3.30 s | **3.43 s** |
| `/games/` | deployed, straight after (edge warm) | 0.18 s | 0.38 s | 0.44 s |
| `/games/` | deployed, 150 ms latency, ~1.1 MB/s | 0.83 s | 2.00 s | 2.11 s |
| `/games/` | local production build | 0.08 s | 0.24 s | 0.33 s |
| `/demos/` | deployed | 0.65 s | 0.68 s | 0.40 s (cards), 0.98 s (thumbnails) |
| `/` | deployed | 0.57 s | 0.56 s | 0.62 s |

The first two rows match the "about 5 seconds uncached" report. The CPU
profile of the local `/games/` load puts all of `generateThumbnails` (seven
games started headless, advanced up to 2 s of game time, rendered to
textures) at **97 ms**, and nothing on the page ran for longer than 50 ms.
The work is not the problem.

The waterfall of run 2 shows where the time goes:

| From | To | What |
| ---: | ---: | --- |
| 0.00 s | 0.46 s | the HTML |
| 0.46 s | 1.38 s | 16 module chunks (~830 KB, ~260 KB gzipped), all requested at once, finishing in three waves |
| 1.41 s | 1.68 s | Pixi's `browserAll` and `init` chunks, which `app.init()` imports only when it runs |
| 1.73 s | 3.30 s | five games' texture sheets, **one after another** (`generateThumbnails` awaits each game's `load()` in turn), ~0.27 s each |
| 3.30 s | 3.43 s | thumbnails, then the cabinet's first frame |

Two things make each step cost a quarter to a third of a second:

- **A cold CDN edge.** GitHub Pages serves through a cache with
  `max-age=600`. On run 2, each texture sheet took ~270 ms. Seconds later,
  in row 3, the same requests took ~14 ms each. The likely reading is that
  each request on a cold edge waits for a fetch from origin. A visitor
  arriving when nobody has loaded the page in the last ten minutes, which
  for this site is most visitors, pays that on every step in the chain.
- **HTTP/1.1.** The site is served only over plain HTTP (section 4.4), so
  the browser opens at most six connections and the 16 chunks queue in
  three waves. HTTP/2 would send them together.

So the measure that matters is the number of **serial round trips** before
first content. `/games/` has about ten. The latency-throttled row,
taken with the connection and edge already warm, shows the same chain
costing 2.1 s at 150 ms a trip.

## 4. Loading: recommendation

**No site-wide loading progress screen.** A splash screen would make the wait
visible, but no shorter. The Arcade can instead avoid having most of the
wait at all.

### 4.1 The Arcade's first paint needs only HTML, CSS and one small chunk

The Arcade page loads the HTML JSX runtime, the Arcade's model and view,
and each entry's metadata (section 6): no Pixi, no three.js, no entry code, no
textures. Thumbnails are ordinary `<img loading="lazy">` files (section 9):
they fill in as they arrive and block nothing. That is about three serial
round trips (HTML, CSS and JS, images), roughly 1 s on a cold edge over
HTTP/1.1, and less over HTTP/2. To be measured after step 9 (section 11),
with a target of under 1.2 s cold, from the same script as section 3.

A **size budget** keeps it that way: a check in `packages/checks/` that builds the
website and fails if the home page's initial JS includes `pixi.js` or
`three`, or exceeds a set gzipped size (to be set from the first
measurement).

### 4.2 An entry loads under the zoom

Launching an entry imports its chunk (and Pixi or three.js the first time),
then its assets. The zoom into its card takes ~600 ms. Loading starts when
the zoom does, not after it, so a warm or fast load is hidden by the zoom.
When loading takes longer, the zoom ends on the entry's thumbnail filling
the play area, with a thin progress bar along its foot, until the entry is
ready (section 10.2).

Three things shorten that load:

- **Load on intent.** Hovering or focusing a card, or a `touchstart` on
  it, starts its `load()`. People rest on a card for a few hundred ms
  before they click it.
- **Prefetch the renderers when idle.** Once the Arcade has painted and the
  network is quiet (`requestIdleCallback`), prefetch the Pixi chunk, since
  most entries need it. Leave three.js to load on intent.
- **No serial asset loads inside an entry.** An entry's `load()` starts its
  requests together (`Promise.all`), and none waits on another without
  needing its result.

Pixi's own late chunks (`browserAll`, `init`) add a round trip after
`app.init()`. Pixi 8's `manageImports: false` option, with the extensions
imported directly, would bring them into the first wave. Worth trying once
the rest is done; with the prefetch above, it may not matter.

### 4.3 Progress, honestly

`load()` takes an `onProgress(fraction)` callback. Fetching an entry's chunk
(a dynamic `import()`) gives no progress events, so the bar sits
indeterminate until the chunk arrives. From then on it follows the assets
(Pixi's `Assets.load` reports progress). If an entry reports nothing, the
bar stays indeterminate until the entry is ready. This is cheap, and it
never claims progress that hasn't happened.

### 4.4 HTTPS and HTTP/2

`https://yortus.com/mvt-games/` fails the TLS handshake with
`SEC_E_WRONG_PRINCIPAL`: the certificate is not for `yortus.com`. GitHub
Pages issues one for a custom domain once DNS points at it. Removing the
custom domain and adding it again in the repository's Pages settings usually
starts that. With a certificate, turn on "Enforce HTTPS". GitHub Pages then
serves HTTP/2, which collapses the chunk waves of section 3.2 into one.

This is a settings change, not code, and is independent of the rest. It
also matters on its own. Browsers mark plain HTTP pages "Not secure". And
the four libraries' READMEs and `package.json` `homepage` fields link to
`https://yortus.com/mvt-games/docs/`, which fails today. Those links ship to
npm with every release.

### 4.5 A quick win before the Arcade

If the Arcade is some way off, one change to today's cabinet takes most of
the five texture sheets' 1.6 s off the first load: load every game's assets
together (`await Promise.all(games.map((g) => g.load?.()))`) before the
thumbnail loop, instead of one at a time inside it. That is optional, and
a few lines. The Arcade replaces this code anyway.

## 5. The Arcade

### 5.1 Name

**Arcade.** It fits "MVT Games", the cabinet's zoom it keeps, and the
Era tags. Arcades always had demos running in attract mode beside the
games, so a demo or an art piece belongs there too. Considered: *Gallery*
(neutral, but flat for games) and *Games* (a demo or an art piece is not a
game). Settled 2026-10-04; do not reopen without new information.

### 5.2 Where it lives

The Arcade is the home page, `/`. A short introduction (what MVT is, a link
to the docs) sits above the card wall, which takes the rest of the page.
Docs and Playground stay in the nav bar. The nav loses Games and Demos and
gains nothing: Arcade is the brand link.

An entry is addressed by the URL fragment: `/#crumb-chase` launches Crumb
Chase directly, as `/games/#crumb-chase` does today. Active filters live
in the query (`/?type=game&era=1980s`), so a filtered Arcade can be shared,
and survive a reload. Both are written with `history.replaceState`, not
pushed, as now.

The old pages become static redirect stubs (a `<meta http-equiv="refresh">`
plus a one-line script that keeps the fragment): `/games/#id` and
`/demos/#id` to `/#id`, `/demos/boids-3d/` to `/#boids-3d`, and
`/demos/fruit-machine/` to `/#fruit-machine`. Links to the site from outside
keep working.

*Changed in step 9:* no redirects. Nobody uses the old addresses yet, so the
old pages were simply deleted (section 11.16).

### 5.3 Built the MVT way, in HTML JSX

As 026 asked: an `ArcadeModel`, and an `ArcadeView` in HTML JSX
(`/** @jsxImportSource @mvtjs/html */`) taking `{ model }`, with leaf views
taking bindings: `ArcadeCardView`, `TagFilterView`, `EntryInfoView`,
`RunnerChromeView`, `PauseMenuView` (moved from Pixi to HTML, section 10.3).
It is the first real app screen built with the HTML JSX runtime, so its
findings about that runtime get recorded (026's last criterion), in
`packages/html`'s design notes or a task.

### 5.4 The model

A sketch, to be settled in implementation:

```ts
type ArcadePhase = 'browsing' | 'loading' | 'ready' | 'playing';

interface ArcadeModel {
    readonly entries: readonly ArcadeEntry[];
    /** The entries the filters let through, in catalogue order. */
    readonly shownCount: number;
    readonly shownEntryAt: (index: number) => ArcadeEntry;
    readonly isTagActive: (tag: Tag) => boolean;
    readonly phase: ArcadePhase;
    readonly activeEntry: ArcadeEntry | undefined;
    /** 0 to 1, or undefined while the entry gives no progress. */
    readonly loadProgress: number | undefined;
    readonly toggleTag: (tag: Tag) => void;
    readonly clearTags: () => void;
    readonly launch: (id: string) => void;
    /** Reported by the view once its zoom has finished, so play starts on screen. */
    readonly startPlaying: () => void;
    readonly exit: () => void;
    readonly update: (deltaMs: number) => void;
}
```

`launch` starts the entry's `load()` and moves to `'loading'`. When the load
resolves, the model moves to `'ready'`. `startPlaying` moves from `'ready'` to `'playing'`.
The view calls it once its zoom has finished, as `onLaunchPressed` works in
the cabinet now, so no game time passes under the zoom. The model holds no
session: the host starts and destroys sessions when the phase changes
(section 10.1), as the runner does today. A failed load returns to
`'browsing'` with an error the card shows.

## 6. Entries

### 6.1 Metadata now, code later

An `ArcadeEntry` is everything the Arcade shows without running anything,
plus a lazy `load()`:

```ts
interface ArcadeEntry {
    readonly id: string;
    readonly name: string;
    /** One or two lines, on the card. */
    readonly summary: string;
    /** A paragraph, in the info panel. */
    readonly description: string;
    readonly tags: EntryTags;
    /** When the entry joined the site (ISO date), for the "newest first" sort. */
    readonly added: string;
    /** The entry's play area, for the card's aspect ratio and the runner's scaling. */
    readonly screenWidth: number;
    readonly screenHeight: number;
    readonly integerScale?: boolean;
    readonly instructions?: string;
    readonly techniques?: readonly string[];
    /** The thumbnail image's URL (section 9). */
    readonly thumbnail: string;
    /** Imports the entry's code and loads its assets. */
    readonly load: (options: { onProgress: (fraction: number) => void }) => Promise<EntryStarter>;
}
```

Each entry's directory barrel exports only its `ArcadeEntry`. Its `load` is
`() => import('./crumb-chase-entry')` plus the asset loads. A dynamic import
of a file in the same directory keeps within the barrel rule, and gives every
entry its own chunk.
The website's entry list (`website/src/entries/index.ts`) imports the
barrels, and so the metadata only. `thumbnailAdvanceMs` moves to the
loaded part (section 6.2), since only the thumbnail script uses it.

### 6.2 Two kinds of entry

What `load()` resolves to says how the entry runs:

```ts
type EntryStarter = PixiEntryStarter | ElementEntryStarter;

/** The host owns a Pixi app and gives the entry a container on its stage, as now. */
interface PixiEntryStarter {
    readonly kind: 'pixi';
    readonly thumbnailAdvanceMs?: number;
    readonly start: (options: { stage: Container; host?: PixiHost }) => EntrySession;
}

/** The entry owns its renderers (three.js, Pixi, the DOM, or several) and mounts into an element. */
interface ElementEntryStarter {
    readonly kind: 'element';
    readonly thumbnailAdvanceMs?: number;
    readonly start: (options: { element: HTMLElement }) => ElementEntrySession;
}

interface EntrySession {
    /** Advances the entry's models only. */
    readonly update: (deltaMs: number) => void;
    readonly resize?: () => void;
    readonly destroy: () => void;
    readonly inputConfig?: EntryInputConfig;
}

interface ElementEntrySession extends EntrySession {
    /** The entry's view roots, of any renderer, for the host's `updateView` and `refreshView`. */
    readonly views: readonly ViewRoot[];
    /** Draws a frame with the entry's renderers, after the host has refreshed its views. */
    readonly render: () => void;
}
```

**Why two kinds and not one.** 026 asked whether one renderer-neutral
`start({ element })` would read better. For the ten Pixi entries, it would
not. Each would create its own `Application`, and the host would lose what
it gives Pixi games today: the shared app, touch controls drawn around the
play area, integer scaling, and pausing by leaving the game's container out
of `updateView`. The benchmarks start Pixi entries headless on a bare
`Container`, which a renderer-neutral start would rule out. So Pixi keeps its
shape, and everything else is an `element` entry.

**The host still drives the tick for `element` entries.** It calls
`session.update`, then `updateView` and `refreshView` on `session.views`
(the same functions for every renderer), then `session.render()`. Pausing
stays the host's call: it skips `update` and `updateView` and still
refreshes. Boids in 3D's camera orbit, which its page advances by hand in
its loop today, becomes a `setUpdate` on the camera's rig, so it pauses
with everything else.

The Fruit Machine mounts its four quadrants into the element as its page
does now. Its page CSS moves into a stylesheet its `load()` imports.

### 6.3 Games and demos merge

`GameEntry`, `DemoEntry`, `GameSession`, `DemoSession` and `DemoHost` go;
`ArcadeEntry`, the two starters and `EntrySession` replace them, in
`website/src/entries/`. The directories `website/src/games/` and
`website/src/demos/` stay as they are, since "game" and "demo" are still how
the code is organised. Only the entry types and the lists are shared. A
future art piece goes in `website/src/art/<name>/`.

### 6.4 The benchmarks import entries by name

`website/package.json` exports the entry list:

```json
"exports": { "./entries": "./src/entries/index.ts" }
```

`benchmarks` declares `"@mvtjs/website": "*"` and imports
`@mvtjs/website/entries`. A
benchmark awaits `entry.load(...)` and checks that the starter is `pixi`. The
`games-and-demos` suite runs only Pixi entries, as it does now.

## 7. Tags and filtering

### 7.1 The groups

```ts
interface EntryTags {
    readonly type: 'game' | 'demo' | 'art';
    /** The era an entry is in the style of. Left out where there isn't one. */
    readonly era?: '1970s' | '1980s' | '1990s' | '2000s' | '2010s';
    readonly genres: readonly Genre[];
    /** For someone choosing an entry's source to study. Picked by hand. */
    readonly level: 'starter' | 'intermediate' | 'advanced';
}
```

- **Type, Era, Genre, Level** are written in each entry, as string-literal
  unions. `Genre` is a closed union in `entries/`, so a typo is a type
  error and the filter bar's chips come from the union.
- **Renderer** (Pixi, three.js, HTML) is a fifth group, not in the original
  list but cheap and useful to someone studying the code ("show me the
  three.js ones"). It is **measured**, not written (section 7.2).
- **Size**, the entry's lines and files, is measured and shown in the info
  panel and on the card's foot, beside Level. It is not a filter: size is
  not difficulty, which is why Level is picked by hand (settled 2026-10-04).

### 7.2 Measured at build time

### 7.3 How filtering behaves

- Within a group, chips are OR: 1970s *or* 1980s. Across groups, AND: a
  1980s *game*.
- Each chip shows how many entries it would leave showing. A chip that would
  leave none is disabled, not hidden, so the bar does not jump about.
- An empty group (Type: art, today) shows no chips at all.
- "Clear" resets them all. The query string follows the chips (section 5.2).
- A sort control beside the chips orders the wall: as listed (the
  default, hand-curated), by name, by era (undated entries last), or newest
  first (by `added`). The query string keeps it too (`?sort=newest`).
- The filter bar sticks to the top of the page under the nav. On a phone
  it collapses to a "Filters" button that opens it as a sheet.

## 8. The card wall

### 8.1 Columns

Cards of one width in as many columns as fit (about 280-340 px each, one
column on a phone). Each card goes in the shortest column so far, in
catalogue order. Every card is the same size (section 11.3), so the
columns stay even.

The layout is a **view model**, `createCardWallLayout()`, owned by the
Arcade view. Given the column width, the gap and each card's height, it
places every card and eases them to new places when the filters or the
width change. Its `update(deltaMs)` advances the easing, and `refresh` writes
each card's `transform`. Cards that a filter removes fade and shrink out,
and cards it brings back fade in. Being plain TypeScript, the layout is
unit-tested without a DOM.

Card heights: the image's height follows from the entry's aspect ratio and
needs no measuring. The text block below it varies with the summary's
length and the font, so a `ResizeObserver` reports each card's height as it
changes. That is an input event to the presentation state, like a key press,
so no layout is read in `refresh`.

**Considered and not recommended:**

- *CSS columns* (`columns: 300px`) place cards down each column in turn,
  so the reading order runs down, not across, and cards cannot glide to new
  places when the filters change. Do not reopen without new information.
- *CSS masonry* (`display: grid-lanes`, the specified form of masonry
  layout) would do the placement natively. When it is in every browser the
  site supports, the layout view model could hand placement to it and keep
  only the animation. Check its support when implementing.

### 8.2 A card

The thumbnail, with a small renderer badge in a corner; the name; the
summary; then a row of chips for type, era and level; and at the foot the
measured size ("1.3k lines, 20 files"). The whole card is a link
(`<a href="#crumb-chase">`), so middle-click and "open in new tab" work, and
Enter on a focused card launches it. An ⓘ button opens the info panel:
description, techniques, instructions, all tags, size, and a link to the
source on GitHub (`sourceUrl` is derived from the entry's directory, not
written by hand).

Hover and focus lift the card and brighten its border, as the demos gallery
does now. Those are plain CSS transitions on styling, not presentation
state.

## 9. Thumbnails

**Generated by a script and committed**, like the textures, not rendered at
page load. Rendering at load needs every entry's code and assets, and a
WebGL context, before the Arcade can show a picture, which is what makes
`/games/` slow. It also can't capture an `element` entry such as the Fruit
Machine's four quadrants (026's open question).

`npm run generate-thumbnails -w @mvtjs/website`:

1. Starts the Vite dev server, and **one** headless Chrome with a
   persistent profile under `node_modules/.cache/` (each new profile costs
   a failed Windows logon on Chrome 153+; see the benchmarks driver).
2. For each entry, opens a dev-only page (`website/snapshot.html`, left out
   of the build) at `?entry=<id>`. The page starts the entry at its play size, advances
   it `thumbnailAdvanceMs` in 16 ms steps (updating models and views, as the
   cabinet's `generateThumbnails` does now), refreshes once, renders once, and signals
   that it is done.
3. Screenshots the entry's element through the DevTools protocol, which
   captures any mix of canvases and DOM, and writes
   `<entry dir>/thumbnail.webp` at 2x the card width.

The entry's metadata imports it (`import thumbnail from './thumbnail.webp'`),
so Vite fingerprints it. Twelve WebP images at ~600 px wide come to roughly
200-300 KB in all, loaded lazily as cards scroll into view. A test checks
that every listed entry has one. When an entry changes how it looks, its
author reruns the script, as with `generate-textures`.

## 10. Launching, zoom and the runner

### 10.1 One page, one loop

`website/src/main.ts` runs one `requestAnimationFrame` loop for the whole
page:

1. `arcade.update(deltaMs)`, then, while an entry is playing and not
   paused, `session.update(deltaMs)`.
2. `updateView` and `refreshView` on the document body (the Arcade, the
   runner chrome and the pause menu), and on the entry's roots: the Pixi
   stage for a `pixi` entry, `session.views` for an `element` entry. An
   `element` entry's DOM views are under the body anyway; its three.js and
   Pixi scenes are not.
3. Render: the Pixi app for a `pixi` entry, `session.render()` for an
   `element` entry.

The Pixi `Application` is created on the first `pixi` launch, with
`autoStart: false` (the page's loop drives it, as the Fruit Machine's page
does), and **kept** between launches with its canvas detached, not destroyed
and rebuilt as the demos runner does now.

### 10.2 The zoom

As the cabinet does it, now in HTML:

1. **Zoom in.** The card is clicked or Entered. The view reads the card's rectangle
   in the event handler (not in `refresh`), and `model.launch(id)` starts
   loading. A fixed overlay holds a copy of the thumbnail at the card's
   rectangle, and over ~600 ms grows it to where the entry will be drawn
   (letterboxed in the viewport by the entry's aspect ratio, as the runner
   scales now). The wall behind dims and drifts back.
2. **Hold, if need be.** If the model is still `'loading'` when the zoom
   ends, the thumbnail stays full-size with the progress bar (section 4.3)
   along its foot.
3. **Hand over.** Once the model is `'ready'` and the zoom has finished, the
   view calls `startPlaying`. The host starts the session in the runner's
   element, and the thumbnail fades out over the first frames of the real
   thing.
4. **Zoom out.** On exit, the entry's last frame is copied (for a canvas,
   `drawImage` into one kept for the purpose; otherwise the thumbnail), the
   session is destroyed, and the zoom runs backwards to the card, which the
   wall has kept scrolled into view.

All of it is the Arcade view's presentation state: `update(deltaMs)`
advances the zoom's time, and `refresh` writes the overlay's `transform` and
`opacity`. It is valid from construction, and can be paused and unit-tested,
as the cabinet's is.

A deep link (`/#fuel-run`) starts at step 2 with the thumbnail already
full-size: no zoom, because no card was clicked.

**Considered and not recommended:** the View Transitions API
(`document.startViewTransition`). It morphs one rectangle into another for
free, but it runs on the browser's clock, outside the tick. It cannot hold on
the thumbnail while loading, and while it runs the page underneath is
frozen. Do not reopen without new information.

### 10.3 The runner's chrome

- **Back, pause, fullscreen, info** buttons, in HTML, for every kind of
  entry, in place of the cabinet's hand-made `<button>`s and the demos
  runner's back button. Escape pauses a game, and exits a demo, as now.
- **The pause menu moves from Pixi to HTML**, so it works over any entry.
  Resume, Restart, How to play (from `instructions`), Exit, as now. Pausing
  stays the host's call (section 6.2).
- **Touch controls stay a Pixi view** for `pixi` entries, drawn in the
  margins of the Pixi canvas as now. Moving them to HTML would let `element`
  entries use them too. None needs them yet, so that is left to a later
  task.
- The scaling rules (`fitCanvasToScreen`: integer scaling on desktop,
  margins for touch controls, the orientation hint) move across unchanged
  for `pixi` entries. An `element` entry gets the whole area below the
  chrome, and its own `resize`.
- The nav bar hides during play on touch devices, as now.

### 11.1 Notes from steps 4 to 8

Where the build differs from the design above, and why.

- **No load progress.** `load()` takes no `onProgress` (section 4.3): every
  entry's assets are one small spritesheet at most, which reports nothing
  useful, so the waiting bar is always indeterminate.
- **More on the starter.** `integerScale` and `thumbnailAdvanceMs` live on
  the Pixi starter, not the metadata, since only running code needs them.
  It also has `pixelArt` (nearest-neighbour textures, no antialiasing,
  whole-pixel positions: what the cabinet set for every game) and
  `fitsViewport` (Boids, whose layout follows the window). A Pixi
  application's antialiasing is fixed when it is made, so the host keeps one
  and makes a new one only when the next entry's `pixelArt` differs.
- **Metadata sizes are written out.** An entry's `screenWidth` and
  `screenHeight` are numbers in its metadata, since the views that define
  them would bring Pixi with them. In development, the Arcade asserts that
  they match the starter's.
- **The list is `catalogue/`**, apart from the types in `entries/`, so the
  two do not import each other. The benchmarks import
  `@mvtjs/website/catalogue` and `/entries`, and the falling-sand demo's
  `models` and `views` barrels by subpath.
- **One loop, Pixi included.** The host's Pixi application is not started:
  the page's loop steps its ticker (`ticker.update(time)`), so listeners on
  it, such as `createPerformanceMetrics`, still run each frame, in order.
- **The zoom aims at the play area as it will be.** `playRectFor` is
  followed through the zoom, since loading can change it (a starter's
  integer scaling, a game's touch controls).
- **`isTouchDevice` moved** to the runner, and `#shared` re-exports it:
  importing `#shared` would bring Pixi into the Arcade's first chunk.

What building the Arcade showed about the HTML JSX runtime (026's last
criterion), for step 10 to file in its design notes:

- **Changing styles.** Cards and the zoom move every frame, and `style` is
  fixed, so each uses an `onRefresh` step with its own change checks. An
  attribute per style property, or for CSS custom properties, would remove
  that boilerplate.
- **A hidden element's `onRefresh` does not run.** Focus-on-open logic
  never saw its dialog close, until it moved to an always-visible wrapper.
  Worth a sentence in the docs.
- **`memoiseLast` takes primitives only**, so values derived per entry are
  keyed by its id.
- **`<img>` has no `loading` attribute**, and `loading` must be set before
  `src`, which starts a load: lazy images need a `ref`.
- **Elements made outside JSX can be children** (the host's stage element),
  which made the runner simple.

A loose end: two games name sprites alike, so loading both in one page logs
Pixi's "[Cache] already has key" warnings. The cabinet already did, loading
every game for its thumbnails; in the Arcade it happens only after playing
both.

  down beneath it, group by group with their counts; typing narrows them to
  those with a word that begins with what is typed. Clicking one, or Enter
  (on the first match, or the one the arrow keys moved to), puts it in the
  box as a token with a button to remove it, and clears the words typed to
  find it. Backspace in an empty box removes the last token, Escape closes
  the list, and `/` anywhere on the page jumps to the box.
- **What is typed searches too**: an entry shows if each word is in its name
  or begins one of its tags (`sim` finds the simulations), so typing filters
  the wall at once, before any tag is chosen.
- **Every token narrows.** A tag bar's chips could fairly be alternatives
  within a group; tokens in a search box read as "and", so an entry must now
  have every tag chosen. The list offers only tags that would narrow what
  the tokens let through: none that every such entry has (Pixi, among the
  shooters), and none that no such entry has.
- **The URL keeps the search**: the tags as before (`?genre=shooter`), and
  the words as `q` (`?q=sand`).

### 11.10 The keyboard, and smoother reflow

Further changes at the author's request (2026-10-05):

- **The introduction is back, behind an (i)** beside the title
  (`AboutView`): the paragraph, the link to the docs, and the keys. It opens
  beneath the button, and closes on Escape, a press anywhere else, or the
  button.
- **Cards slide back in.** Removing a tag made every card jump to its new
  place, though adding one slid them. A hidden card measures 0 high; the
  wall took that, so a card shown again, or one shown for the first time,
  looked like a first measure, which snaps the wall to correct an estimate.
  Now a 0 is ignored, a first measure snaps only when it is off its
  estimate (every card is the same size, so it never is), and a card that
  had faded out reappears in its new place, fading in, rather than sliding
  from where it vanished.
- **Tokens keep the order they were chosen in** (`activeChipAt`), so the
  newest is always last, by the caret, where Backspace removes it. A URL
  holds no order: its tags count as chosen in the chips' order.
- **Titles are denser still**: letter spacing -0.02em.
- **The keyboard** (`CardWallView`, `card-wall-keys.ts`): the wall is one
  stop for Tab, its selected card (a roving `tabindex`; the info buttons
  are out of the order). The arrows, or W, A, S and D, move the selection,
  left and right through the order shown and up and down a column, scrolling
  it into view clear of the nav; Enter or Space plays it, and `i` opens its
  info panel. The selection is the wall's presentation state: the card last
  moved to or focused, or the first shown if that one is not. The focus
  rings the whole card. While an entry or an info panel is up, the wall
  ignores keys and lets go of the focus, so a game's keys never move it; it
  takes the focus back, without scrolling, on return.

### 11.11 Slower arrivals, and searching descriptions

Further changes at the author's request (2026-10-05):

- **Cards arriving are seen to arrive.** Cards shown again when a tag was
  removed did fade in, but within about 250 ms, most of it in the first
  100, and while the cards sliding off their places were still there, so
  they read as appearing at once. Now, on a reflow, an arriving card waits
  120 ms for its place to clear, then fades in more slowly (`FADE_IN_MS`,
  about 400 ms in all); a card leaving still fades fast (`FADE_OUT_MS`).
- **Typing after removing a tag works.** Pressing a token's remove button
  took the focus from the box, and the button then went with its token,
  leaving the focus nowhere: typing did nothing. Presses on the box's
  buttons now leave the focus in the box, and removing a token puts the
  caret back in it. Search by name itself was never broken.
- **Words search the descriptions too**: a word typed matches an entry if
  it is in its name, begins a word of its summary, description or
  techniques (`flock` finds both boids demos), or begins one of its tags.
- **Titles' letter spacing is 0**, halfway between the two before.
- **The About note's keys** read as keys, one to a line with what they do:
  the arrows or WASD, each one key; Enter or Space; and `i` "Show more info
  about the selected item".
- **The scrollbar's space is kept** (`scrollbar-gutter: stable` on the
  page). A search short enough to fit the window took the scrollbar away,
  widening the wall, and a new width snaps every card to its place rather
  than sliding it; an entry starting (the page stops scrolling) widened it
  too. The wall is now the same width either way. Overlay scrollbars
  (phones, macOS) never took space, and are unaffected.

### 11.12 Selecting a card

Further changes at the author's request (2026-10-05). A card's selection
was the keyboard's alone, and the polaroid's zoom a CSS hover effect. Now
one card at a time is selected, and the selection is what zooms it:

- **Only the polaroid is the link.** The link takes no pointer events
  except on its polaroid, so hit-testing follows the polaroid exactly as
  drawn, tilted, or lifted and straight. A click anywhere else on the card,
  the title, the foot, or the square around the polaroid (a corner of the
  tilted polaroid's box included), selects the card and does not launch it.
  The info button still opens the panel.
- **Pointing at a polaroid, or holding it, selects its card**, as hovering
  zoomed it before; the selection stays when the pointer leaves, until
  another card is selected.
- **The selected card is shown** by its straightened, closer polaroid and
  an accent border; the keyboard's focus is always on the wall's selected
  card, so the focus ring is gone. Pointing moves the selection but not the
  focus (it must not take it from the search box), so the wall's keys,
  Enter included, act on the selected card wherever on the wall the focus
  is. A click selects and focuses the card, for the keys to go on from.
- **The Tab stop** is the selected card, or the first shown when none is,
  or the selected one is filtered out (which then shows no card selected).
- **A second click deselects** (2026-10-05): a click outside the polaroid
  of the selected card leaves no card selected.
- **The selected card is ringed and glows in its own colour** (2026-10-05),
  in place of the accent border: a dark gap, a ring in its candy colour,
  and a soft glow of it, eased in and out.

### 11.13 A new way in and out: burn, and a tube powering on

At the author's request (2026-10-05). The zoom into an entry landed on the
right place, but still jumped: the entry started blank and faded in, and
started in another state than its thumbnail showed. Rather than fix those,
the way in no longer shows the picture and the entry together.
`TransitionViewModel` (`transition-view-model.ts`) replaces the zoom's view
model, `TransitionView` its view, and `WallEffectView` draws on the wall.

Two ways were tried, each with the burn below: the picture zooming to the
play area and turning edge-on, the entry turning in behind it (a flip); and
the picture receding, the entry's screen powering on like an old tube.
The author chose the tube, without the zoom to the play area, and then
with the polaroid floating to the centre instead (2026-10-05):

- **In**: as every other card, and the chosen card's own title and foot,
  burn away, nearest first, the chosen card's polaroid, white border and
  all, floats from its card to the centre of where the entry will play,
  its own size, straightening. The entry loads meanwhile, and a slow load
  holds the polaroid there with its waiting bar. The page blacks out, the
  polaroid recedes into the dark, and the entry is told to start
  (`onHandOver`, the model's `startPlaying`). Once it is running, so has
  drawn a frame, its screen powers on from that centre: a white-hot line
  across the middle (a glow drawn over it, so it is white whatever the
  picture's colours), opening out to the picture. Neither a blank first
  frame nor a thumbnail out of step can show.
- **Out**: the entry's last frame powers off, to a white-hot line and then
  a dot, where it played (remembered at the hand-over: without the entry's
  starter, the play area works out differently, by whole-number scaling).
  The polaroid comes forward out of the dot and floats back onto its card,
  and the cards develop around it, nearest first. An entry whose renderer
  gives no last frame (three.js, HTML) powers off its thumbnail. Leaving
  before the entry started floats the polaroid straight back.
- **The page cannot scroll** until the way out has ended, as while the
  entry plays: the polaroid and the developing cards are placed in the
  window, and would part from the wall.
- **The burn** is one WebGL fragment shader on a canvas over the wall: per
  card, a front creeping from a corner, ragged with noise, painting the
  page's background in behind an ember edge, with scorching ahead of it.
  Developing goes from the background to a mottled blank, which clears to
  the card. Without WebGL, the cards just fade.
- The power-on is a CSS transform on the stage's element, so it works alike
  for Pixi, three.js and HTML entries. The card's own polaroid hides while
  the transition carries it.
- **Less motion, for those who ask for it** (`prefers-reduced-motion`, the
  visitor's system setting, read as each way in or out starts): the way in
  fades the page to black round the polaroid, the polaroid, then up into
  the entry, and the way out fades the last frame, then the page back with
  the polaroid on its card, 250 ms each; nothing burns, floats or flashes.
  The wall's cards jump to new places rather than slide (they still fade),
  the polaroid lifts without animating, and the keyboard scrolls at once.
  The entries themselves are left as they are: their motion is what the
  visitor chose to see, which the setting does not ask to take away.
- Still to tune: each card burns for 700 ms, spread over 250 ms; the
  polaroid floats for 700 ms, recedes in 300 ms; the screen powers on in
  500 ms.

### 11.20 Attract mode

Step 11, on 2026-10-05:

- **A card that stays selected for a second plays its entry live** over its
  photo: hovering its polaroid selects it, and so do the arrow keys. It
  stops the moment another card is selected, and that one waits its own
  second. One at a time.
- **The page plays it**, in a second entry host (`playLive` in
  `arcade/main.ts`), ticked in the same loop. The wall decides which card,
  through an attract view model (`views/attract-view-model.ts`, with tests),
  and reports it (`onLiveWanted`); the card shows the host's element over
  its photo, faded in once it has drawn three frames. The model never knows.
- **Drawn at its play size, scaled and cropped as the photo is**, so the
  live picture lines up with the thumbnail it covers. The entry host now
  measures its element's own size, before transforms (`offsetWidth`), which
  this needs.
- **Non-interactive.** The host takes an option, `takesInput: false`: no
  keyboard input, no touch controls. The card's live layer is `inert`, with
  no pointer events, so a press goes to the card under it. Muted needs
  nothing: no entry plays sound.

  WebGL renderer plays (its measured renderers: Pixi or three.js, with or
  without HTML), so the Fruit Machine, with Pixi and three.js, keeps its
  photo. Boids in 3D plays: preparing an entry that brings its own renderer
  makes a host let go of its Pixi application, and the next Pixi entry
  makes another. Both three.js entries now call `forceContextLoss()` after
  `dispose()`, which keeps the context until it is collected; Pixi's
  `destroy` already lets go of its own. Eight swaps between the two Boids
  cards leave two canvases on the page, the burn's and the preview's.
- **Boids lays itself out for the area it is given.** It read the window,
  less a nav bar the Arcade no longer has, so it never quite fitted the
  runner, and its preview could not match its thumbnail. The Pixi starter's
  `fitsViewport` is now `fitTo(width, height)`: the host calls it as it
  prepares and starts the entry, and as its area changes, then the
  session's `resize`. Boids is designed around 960 by 605, which lays out
  exactly (the arena beside its controls), as its entry now lists; the
  development check fits it to that and compares, and the snapshot page
  photographs it there (thumbnail taken again, crop 600 by 492: the arena).
  A tall, narrow area still puts the controls below.
- **Not on a touch screen**, which has no pointer to rest on a card, **nor
  for reduced motion**, and only while the wall is active: not under an
  entry, an info panel or a transition. Launching the entry playing live
  stops the preview, and the entry plays as before.
- The home page's first load is 34.1 KB of its 40 KB budget, still with no
