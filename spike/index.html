pixi-mvt spike

Scene-wide onUpdate(deltaMs) and onRefresh() for Pixi containers, guaranteed to run every container before any of its descendants.

What to watch.

probe order reads p1 > p2 > p3 > p4. The chain is attached first and p2 is given its refresh method afterwards, once p3 and p4 are already listed. An append-ordered list, which is what Pixi's own onRender keeps, would call p2 last; the trace shows it in tree position instead. onUpdate and onRefresh both fire on every container each tick, regardless of visible; either can return SKIP_DESCENDANTS to skip that container's descendants for the frame.

update pass and refresh pass are what each pass costs over the whole scene, in microseconds. Raise the spawn rate to churn the scene graph harder and watch what it does to them: every swap dirties the memoised call list, so the list is rebuilt on the next pass.

The swarm view creates and destroys its child views from inside onRefresh. A pass walks a snapshot, so a child created during one is not called until the next pass; each entity view runs its own refresh once at construction rather than showing a frame at the origin.
